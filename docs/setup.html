What it is

A visual countdown for children: turn a dial, a red disk shrinks as the minutes run out, and it rings at zero. One set of SwiftUI sources produces a macOS app and an iPhone app; the iPhone app is on the App Store, released and updated entirely through scripts.

The repository holds three deliverables that share one design and one colour palette:

DeliverableWhereHow it is builtStatus
Browser prototypeindex.htmlSingle static file, Google Fonts, no buildreference only
macOS appswift/swiftc into a hand-rolled .app bundle, ad-hoc signedlocal use
iPhone app + Live Activity widgetios/Hand-written .xcodeproj, xcodebuild archive, altool upload, App Store Connect API for everything else1.1 live 1.2 in review

The browser version came first and fixed the look. The Swift port followed, first as a Mac app because that needs no Xcode project, then as an iPhone app once the layout was proven. Everything Apple-facing (bundle ids, certificate, profiles, metadata, screenshots, age rating, build attachment, review submission) is done with two dependency-free Node scripts that talk to the App Store Connect API directly. Only three things ever needed the web UI, and they are listed under The App Store listing.

Toolchain and principles

The machine that built and shipped this had:

  • Xcode 26.6 with command line tools (gives swiftc, xcodebuild, xcrun altool, xcrun devicectl, xcrun simctl). The AlarmKit code needs the iOS 26 SDK.
  • Node 24. The scripts use process.loadEnvFile() (Node 20.12+) and built-in fetch. No package.json exists and none should be added.
  • macOS system LibreSSL at /usr/bin/openssl. Homebrew's OpenSSL 3 writes a PKCS#12 the macOS keychain rejects; see Signing.
  • A paid Apple Developer Program membership and an App Store Connect API key with the App Manager role (Users and Access, Integrations).

Principles the setup follows

  • No dependencies. Nothing to install on the host, nothing to update, nothing that can break between sessions. Sounds are synthesised, the icon is drawn by code, JWTs are signed with node:crypto.
  • Everything from the terminal. Xcode the IDE was never opened. The project file was written by hand, the scheme is checked in, archive and export are xcodebuild calls, upload is altool, and the listing is API calls.
  • Secrets stay out of git. One .env file, gitignored, loaded by every script; the environment wins over the file. Files are staged by name, never git add -A.
  • The journal is the spec. IOS-PORT.md records each decision and each submission with its date and build number, so the next session knows where things stand without asking.
  • Collect nothing. No networking code at all, which makes the privacy questionnaire and App Review notes trivial. PRIVACY.md says so and the listing links to it on GitHub.

Shared Swift sources

One directory, swift/Sources/, compiles for both platforms. The Mac build passes all files to swiftc; the Xcode project references the same files by relative path (../swift/Sources/X.swift) so nothing is copied. Platform differences are handled three ways:

  • Two entry points, one per file. App_macOS.swift and App_iOS.swift each wrap a @main struct … : App in #if os(macOS) / #if os(iOS). Both files are in both builds; the compiler drops the wrong one. The macOS one sets window size and resizability; the iOS one is a bare WindowGroup { TimerScreen() }.
  • Whole files gated. SystemAlarm.swift is entirely inside #if os(iOS) because AlarmKit does not exist on macOS.
  • Small inline gates. Beeper configures AVAudioSession only on iOS and uses a haptic instead of a Dock bounce; DialView drops its NSCursor hover block; TimerScreen uses bigger hit padding on iOS, hides the wordmark text, and owns the iOS lifecycle wiring.

Pattern worth copying

Keep the model free of any view code and keep every #if os() block small and local. The Mac build is then a fast compile check for the shared code (seconds, no simulator), and the iOS project is purely packaging.

The alarm architecture

The one hard requirement was that the timer rings on a locked, silenced phone. Three mechanisms exist in the code, layered by what iOS allows:

  1. In-app beeper (all platforms). AVAudioEngine plays the synthesised pattern every 1.4 s while the app is in front. On iOS the session category is .playback and Info.plist declares UIBackgroundModes: audio, but that only keeps the app alive while sound is actually playing, so a silent countdown gets suspended within seconds.
  2. AlarmKit system alarm (iOS 26+). The real fix. SystemAlarm.schedule creates an AlarmManager timer with the system's full-screen alert, which rings through silent mode and Focus even if the app is killed. It also shows a Live Activity on the lock screen and in the Dynamic Island, rendered by the AlarmWidget extension.
  3. Local notification (iOS 17–25, or permission refused). UNTimeIntervalNotificationTrigger at the end date with the chosen .caf sound. One ding, muted by the silent switch, but better than nothing.

Lifecycle rules in TimerModel

  • The system alarm exists only while the app is off screen. enteredBackground() schedules it inside a beginBackgroundTask grace window; enteredForeground() recomputes remaining from the end date and cancels it. In front, the app rings with its own beeper and shows no system badge.
  • start() asks for AlarmKit permission (falling back to notification permission) because iOS cannot prompt from the background, where the alarm is scheduled.
  • Pause, Reset, changing length, sound, or beep setting cancel or reschedule. Beep "Off" schedules nothing.
  • A scheduled alarm id is kept in UserDefaults. On init the model subscribes to alarmUpdates, so a Stop pressed on the lock screen silences the in-app state too.
  • When the alarm rings while the app is in front, the app only pulses and cuts the system alarm off after the chosen length (1 s / 10 s / 1 min). Locked, it rings until someone presses Stop.

Why there are sound files

AlarmKit and UserNotifications can only play files from the bundle. ios/make-sounds.swift compiles Beeper.swift alongside itself, calls the same Beeper.render for each AlarmSound, repeats it every 1.4 s for 29 s (notifications reject anything over 30 s), and writes IMA4 .caf files. The files are committed; rerun after changing a sound.

The widget extension

AlarmShared.swift declares struct RedWedgeAlarm: AlarmMetadata {} and is compiled into both targets, because the Live Activity must decode exactly the AlarmAttributes<RedWedgeAlarm> the app scheduled with. The widget draws the disk as a ProgressView(timerInterval:), which the system winds down on its own since a widget cannot redraw per frame. The app's Info.plist needs NSSupportsLiveActivities and NSAlarmKitUsageDescription.

macOS build

No Xcode project. swift/build.sh creates the .app directory structure, writes a static Info.plist with a heredoc, compiles all sources with one swiftc call, and ad-hoc signs the result.

swiftc -O -parse-as-library \
  -target arm64-apple-macos14.0 \
  -framework SwiftUI -framework AppKit -framework AVFoundation \
  -o "$APP/Contents/MacOS/RedWedgeTimer" \
  Sources/*.swift
codesign --force --sign - "$APP"

-parse-as-library is required because the entry point is a @main type rather than top-level code. Run with ./swift/build.sh && open "swift/Red Wedge Timer.app". This is also the fastest compile check for shared code changes.

Build settings that matter

  • GENERATE_INFOPLIST_FILE = NO and INFOPLIST_FILE = Info.plist. The plist is explicit, with $(MARKETING_VERSION) and $(CURRENT_PROJECT_VERSION) substituted from the target settings.
  • MARKETING_VERSION and CURRENT_PROJECT_VERSION appear in four places (Debug and Release for both targets) and must agree, or App Store Connect rejects the upload for a version mismatch between app and extension.
  • Debug: CODE_SIGN_STYLE = Automatic, so dev.sh can build for a device with -allowProvisioningUpdates.
  • Release: CODE_SIGN_STYLE = Manual, CODE_SIGN_IDENTITY = "Apple Distribution", DEVELOPMENT_TEAM, and PROVISIONING_PROFILE_SPECIFIER set to the profile name. The same names appear in ExportOptions.plist; all three must match what asc-provision.mjs created.
  • Widget target: IPHONEOS_DEPLOYMENT_TARGET = 26.0, SKIP_INSTALL = YES, extra runpath @executable_path/../../Frameworks, product type com.apple.product-type.app-extension, plist CFBundlePackageType = XPC! with NSExtensionPointIdentifier = com.apple.widgetkit-extension.
  • TARGETED_DEVICE_FAMILY = 1 (iPhone only) on both, which also means only 6.9" screenshots are required.
  • The scheme is under xcshareddata, so xcodebuild -scheme RedWedgeTimer works on a fresh clone.

The Info.plist for the app also carries: ITSAppUsesNonExemptEncryption = NO (skips the export-compliance question on every build), UILaunchScreen as an empty dict (required, otherwise the app is letterboxed), portrait only, UIBackgroundModes: audio, NSSupportsLiveActivities, NSAlarmKitUsageDescription.

Fallback

If writing a pbxproj by hand feels risky for a new app, the documented alternative is to create the project once in Xcode's GUI, commit it, and never open Xcode again. The xcodegen tool is another option, but it would be a dependency.

Dev loop: simulator and device

Simulator, no signing

cd ios && xcodebuild -project RedWedgeTimer.xcodeproj -scheme RedWedgeTimer \
  -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO -derivedDataPath build/sim build

xcrun simctl boot "iPhone 17 Pro"            # or whatever `xcrun simctl list devices` shows
xcrun simctl install booted "build/sim/Build/Products/Debug-iphonesimulator/Red Wedge Timer.app"
xcrun simctl launch booted com.bersling.redwedgetimer

Real iPhone, bypassing the App Store

ios/dev.sh builds the Debug configuration for the paired device (automatic signing, -allowProvisioningUpdates) and installs with xcrun devicectl device install app, then launches by bundle id. The device UDID is baked in as a default and overridable with DEVICE=…. It first checks devicectl list devices for state connected and refuses otherwise, since a stale pairing row looks identical to a reachable phone.

Caveat

The 1.1 and 1.2 AlarmKit path was built and launched only in the simulator before submission. The device install script exists but the install step had not been exercised at the time of writing. Treat a locked, silenced one-minute timer as the first thing to test on a real phone.

Credentials

One file, .env at the repo root, gitignored. Three keys, all for the App Store Connect API:

APPSTORECONNECT_KEY_ID=XXXXXXXXXX          # key id from Users and Access > Integrations
APPSTORECONNECT_ISSUER_ID=xxxxxxxx-…        # issuer UUID shown above the key list
APPSTORECONNECT_P8=/absolute/path/AuthKey_XXXXXXXXXX.p8   # a PATH to the key file, not its contents

Every Node script starts with try { process.loadEnvFile(new URL('../.env', import.meta.url)); } catch {} so the environment wins over the file; the shell scripts do set -a; . ../.env; set +a. The JWT is built by hand: header {alg: ES256, kid, typ: JWT}, payload {iss, iat, exp: iat+900, aud: 'appstoreconnect-v1'}, signed with createSign('SHA256') and dsaEncoding: 'ieee-p1363'. That last option matters; the default DER signature is rejected by Apple.

altool ignores the path variable and looks for ~/.appstoreconnect/private_keys/AuthKey_<KEY_ID>.p8. release.sh copies the key there on first run.

Git hygiene

Because .env sits in the working tree, commits in this repo stage files by name. A blanket git add -A was flagged once as a credential leak risk and is now a rule.

Signing and provisioning

Done once per app, almost entirely through the API with ios/asc-provision.mjs. The one step that touches the keychain is a script the human runs.

  1. Make a private key and a certificate signing request (the CSR is what Apple signs; the key never leaves the Mac): 
    openssl genrsa -out distribution.key 2048
openssl req -new -key distribution.key -out build/distribution.csr \
  -subj "/emailAddress=you@example.com/CN=Your Name/C=CH"
    Keep distribution.key somewhere permanent. The one for this app was generated in a session scratchpad and install-signing.sh copies it to ~/Documents/signing/; a lost key means revoking the certificate and starting over.
  2. Register bundle ids: node asc-provision.mjs bundle-id and node asc-provision.mjs bundle-id --extension. Idempotent; it finds an existing id by identifier first.
  3. Create the distribution certificate: node asc-provision.mjs certificate --csr build/distribution.csr. Writes build/distribution.cer (DER). One certificate serves every app on the team.
  4. Create App Store profiles: node asc-provision.mjs profile and … profile --extension. Each is IOS_APP_STORE type, bound to the bundle id and every distribution certificate on the account, and lands in build/. The profile names ("Red Wedge Timer App Store", "Red Wedge Timer Alarm App Store") are what the Xcode project and ExportOptions.plist reference.
  5. Run ios/install-signing.sh yourself. It converts the DER certificate to PEM, pairs it with the key into a .p12 using /usr/bin/openssl with -certpbe PBE-SHA1-3DES -keypbe PBE-SHA1-3DES -macalg sha1 (Homebrew OpenSSL 3 defaults produce "MAC verification failed" on import), imports into the login keychain with -T /usr/bin/codesign, and copies the profile to ~/Library/MobileDevice/Provisioning Profiles/<UUID>.mobileprovision. It ends by listing security find-identity -v -p codesigning and fails loudly if "Apple Distribution" is missing.
  6. If codesign still cannot find the identity, macOS is withholding the fresh key from command line tools: security set-key-partition-list -S apple-tool:,apple: -k <login password> ~/Library/Keychains/login.keychain-db.

node asc-provision.mjs status prints the bundle id, every certificate with expiry, and every profile with its state. Run it first in a new session.

Release pipeline

ios/release.sh does the binary side in three xcodebuild/altool calls:

xcodebuild -project RedWedgeTimer.xcodeproj -scheme RedWedgeTimer \
  -configuration Release -sdk iphoneos -archivePath build/RedWedgeTimer.xcarchive archive

xcodebuild -exportArchive -archivePath build/RedWedgeTimer.xcarchive \
  -exportOptionsPlist ExportOptions.plist -exportPath build/export

xcrun altool --upload-app -f "build/export/Red Wedge Timer.ipa" -t ios \
  --apiKey "$APPSTORECONNECT_KEY_ID" --apiIssuer "$APPSTORECONNECT_ISSUER_ID"

--no-upload stops after the .ipa. ExportOptions.plist says method = app-store-connect, signingStyle = manual, the team id, uploadSymbols = true, and a provisioningProfiles dict mapping each bundle id to its profile name. After upload, processing takes a few minutes before asc-store.mjs build can see a VALID build.

Precondition

The app record must exist in App Store Connect before the first upload, and the API cannot create one. Make it once in the web UI (name, primary language, bundle id, SKU), then copy the numeric Apple ID into asc-store.mjs.

The App Store listing

ios/asc-store.mjs holds the listing as a constant (LISTING: description, keywords, promotional text, support URL, release notes), the review contact (REVIEW_CONTACT), the app id, the version string, and the locale. Only possible in the web UI

  • App Privacy questionnaire (answered "data not collected", published once; persists across versions).
  • Copyright on the version and the price tier (free). Both block submission, and the API only reports "not in valid state". The version page's "Add for Review" button lists the real blockers; use it as the diagnostic.
  • Export compliance used to be a third one, now avoided by ITSAppUsesNonExemptEncryption = NO in Info.plist.

Shipping a new version

  1. Bump versions in the pbxproj: MARKETING_VERSION (e.g. 1.3) if the user-visible version changes, and CURRENT_PROJECT_VERSION always, in all four configurations. A rejected or pulled build keeps the marketing version and bumps only the build number.
  2. Update asc-store.mjs: VERSION and LISTING.whatsNew.
  3. Build and upload: cd ios && ./release.sh. Wait a few minutes.
  4. Create the version and notes: node asc-store.mjs metadata. Screenshots, age rating, categories and privacy URL carry over; rerun only if they changed.
  5. Attach and submit: node asc-store.mjs build, then node asc-store.mjs submit. With release type AFTER_APPROVAL, approval publishes it with no further action.
  6. Record it in IOS-PORT.md (date, build, what changed, what was not tested) and commit with the pbxproj and script changes together, e.g. "1.2 build 5: the system alarm only while the app is off screen".

Gotchas learned the hard way

  • Background audio does not keep a silent app alive. iOS suspends it within seconds, and a repeating Timer dies with it. Only AlarmKit rings reliably on a locked phone. Critical notification sounds need an entitlement Apple does not hand out.
  • AlarmKit cannot prompt from the background. Request authorization on Start, while the app is in front, even though scheduling happens on background entry.
  • Scheduling in enteredBackground needs a background task, otherwise the async schedule call can be suspended before it lands.
  • Sound files over 30 s fall back to the default notification sound; the generator renders 29 s.
  • App and extension must share version numbers, or the upload is rejected.
  • JWT signature must be ieee-p1363, not DER, or every API call is 401.
  • Homebrew OpenSSL 3's PKCS#12 fails keychain import; use /usr/bin/openssl with SHA1/3DES options.
  • "Not in valid state" from reviewSubmissions means a web-UI-only field is empty. Open the version page and press "Add for Review" to see which.
  • The builds list is unsorted by default; without sort=-uploadedDate the attach step picks last version's build.
  • A device row in devicectl list devices is not a reachable device. Check the state column, or the tunnelState in device info details.
  • The keychain is off limits to the agent. Anything touching security import or ~/Library/MobileDevice is a script the human runs once.
  • Private key in a scratchpad is a trap: scratchpads are deleted. Move the key to a permanent folder before the session ends.

Imitation checklist

To set up a new iPhone app the same way, in order. Names in <angle brackets> are what to change from this repo.

  1. Prototype in one HTML file to settle the look and the colour tokens. Port those tokens to a Palette.swift.
  2. Write shared SwiftUI sources in swift/Sources/ with two @main files behind #if os(). Copy swift/build.sh, change the app name, bundle id and executable name, and use it as the compile check.
  3. Copy ios/ and rename: in project.pbxproj the product names, PRODUCT_BUNDLE_IDENTIFIERs, PROVISIONING_PROFILE_SPECIFIERs, and the source file references; the scheme's BuildableName; both Info.plist display names; ExportOptions.plist bundle ids and profile names. Delete the widget target if the app has no Live Activity (remove F…02, K2…, L…03, the embed phase, the dependency, and the A2 build files).
  4. Write .env with the three App Store Connect keys and make sure .gitignore lists it.
  5. Edit the constants at the top of asc-provision.mjs (BUNDLE_ID, APP_NAME, PROFILE_NAME, PROFILE_FILE) and run status, bundle-id, profile. Reuse the team's existing distribution certificate; only create one if status shows none.
  6. Have the human run install-signing.sh after updating its PROFILE_UUID (read it from the new .mobileprovision with security cms -D -i build/X.mobileprovision | plutil -extract UUID raw -) and key path.
  7. Create the app record in the web UI, copy the Apple ID into asc-store.mjs, and rewrite LISTING, REVIEW_CONTACT, PRIVACY_POLICY_URL, categories, and VERSION = '1.0'.
  8. Generate assets: an icon script, screenshots from the simulator into store/screenshots/.
  9. Add PRIVACY.md and push, so the privacy URL resolves before submission.
  10. Release: ./release.sh, then asc-store.mjs metadata, screenshots, age-rating, categories, privacy-url, review-detail, build. In the web UI set copyright, price, and App Privacy. Then submit.
  11. Start a journal like IOS-PORT.md and record the submission date and build.

Working conventions

  • Commits are a single sentence in plain English describing the user-visible change, no type prefixes, e.g. "Keep the screen on while the disk shrinks, and ship it as 1.1 build 4". Release commits name the version and build. The agent commits and pushes finished work to origin main itself.
  • Documentation lives in three places: swift/README.md for how the app behaves, IOS-PORT.md for decisions and release history, and this file for the setup. Script headers carry their own usage block and are authoritative for flags.
  • Non-trivial changes go through a git worktree so the main checkout, which may be open in an editor, does not churn.
  • No host installs. If a tool is ever needed beyond Xcode and Node, it runs in a container.
  • Sibling repo: ~/IT-Projects/toddler-games/scripts/ has the older generation of these App Store Connect scripts (asc.mjs, asc-metadata.mjs, asc-submit.mjs) plus analytics and Google Play upload. This repo's scripts are the leaner descendants and the ones to copy forward.
